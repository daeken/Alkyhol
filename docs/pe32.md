# PE32 feasibility — research, not implementation

The user asked whether 32-bit Windows binaries can fit the current 64-bit Mach-O
packaging approach. Yes in architectural terms: a 64-bit process can contain
32-bit code segments and switch to 64-bit code at API boundaries. Our wrapper
embeds PE bytes and maps them itself; its Mach-O header does not require every
mapped guest instruction to execute in 64-bit mode. Current Alkyhol runtime
support is **still AMD64 PE32+ only**. No 32-bit mode transition has been tested
on this physical M4, and this note adds no compatibility claim or new priority
over the user's active DLL/runtime work.

## Verified primary-source background

Wine's [macOS WineConf 2022 presentation](https://indico.freedesktop.org/event/2/contributions/92/attachments/87/140/Wine%20on%20macOS%20State%20of%20the%20Union%20-%20WineConf%202022.pdf)
records macOS's ability to create 32-bit code segments in 64-bit processes and
Rosetta 2's support for those segments. The [Wine 9.0 release notes](https://list.winehq.org/hyperkitty/list/wine-announce%40list.winehq.org/message/TB7WYKWZF4DWNQLWN3XZM2NLEAF6MKST/)
describe new WoW64: 32-bit PE modules use thunks into 64-bit Unix libraries, without
needing 32-bit Unix processes. The pinned [Wine 11.0 wow64cpu source](https://github.com/wine-mirror/wine/blob/wine-11.0/dlls/wow64cpu/cpu.c)
shows 32/64-bit code selectors and transition thunks, and rejects a transition
entrypoint above 4 GiB. These are external implementation/specification sources,
not an Alkyhol execution test. Wine code has not been copied into Alkyhol.

## Concrete work needed

- A checked PE32/i386 loader: 32-bit optional headers/import slots, HIGHLOW
  relocations, pointer arithmetic and image limits. The existing static inventory
  scanner already recognizes PE32; the runtime parser deliberately rejects it.
- A guest arena below 4 GiB for code/data, stacks, TEB and callable gateways. Local
  `otool -l` inspection shows the current x86-64 wrapper reserves a 4-GiB
  `__PAGEZERO` and starts `__TEXT` at 4 GiB, so the host link/preload layout must
  change before low guest allocations are possible. Current image mappings do
  not provide that arena.
- Assembly mode-transition gates and explicit 32-bit calling conventions,
  stack cleanup, return values and register preservation. Initial transition code
  must itself be reachable from the 32-bit side; high Rust function addresses
  cannot simply be placed in 32-bit import slots.
- Per-thread Windows state, FS/TEB/TLS, exception/context restoration, callbacks
  and signal boundaries. A basic no-CRT/no-TLS return test proves much less than
  ordinary CRT or game startup.
- 32-bit views of pointer-bearing structures and COM vtables/proxies. Buffer
  addresses may be widened after validation, but nested layouts and returned
  interface pointers require real marshalling. Rust's existing Win64 bridges
  cannot be called directly with a 32-bit stack or vtable layout.

The first useful evidence would be a tiny original PE32 code body entering through
an actual 32-bit code segment and returning to the 64-bit host, followed by an
imported API call and a callback with preserved registers. Run the identical PE
on native Windows as an independent reference. Keep this experimental path
separate from the working PE64 loader until those contracts pass. API semantics
and the direct Metal backend can remain 64-bit Rust, with explicit bridges at
the guest boundary; eventual native decompiler output remains a separate route.
