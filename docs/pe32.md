# Experimental PE32 execution in a 64-bit Rosetta host

Alkyhol now executes an unchanged owned i386 Windows PE32 binary on the physical
M4 through a 64-bit Mach-O host. This is checked loading plus CPU mode gates, not
static instruction rewriting, a 32-bit Mach-O, or a general Win32/game runtime.
The user-selected next application target is their local DAOrigins executable;
it has not executed. Native-backed partial-image-page handling clears its previous
SizeOfImage gate. Native-backed handling of non-mapped certificate metadata now
clears its next file-range gate. Checked static TLS data now clears that startup
gate as well. Legacy cookie configuration is now supported; local preflight
stops at the explicit SafeSEH exception-dispatch gate before entry. Game binaries, packaged game wrappers and all
header/import inventories remain ignored/local and are never sent to CI.

```sh
python3 tools/build_pe32_fixture.py
python3 tools/run_pe32_probe.py --fixture local/pe/pe32/pe32.exe --output local/pe/pe32/observation.json
python3 tools/translate_pe32.py /path/to/trusted.exe --output local/pe/program32-macos
local/pe/program32-macos --inspect
local/pe/program32-macos
```

## CPU and address-space contract

The host links with a 4-KiB __PAGEZERO so low guest address space is available.
MAP_32BIT allocations are checked below 4 GiB without MAP_FIXED or replacing host
mappings. Image bases are 64-KiB aligned; the stack has inaccessible guard pages.
Two unused LDT slots (512/513) supply flat 32-bit code/data descriptors and remain
reserved for this process lifetime. A third slot (514) supplies a per-image FS/TEB
descriptor only during an exclusively leased CPU entry. Occupied slots fail before
being overwritten; concurrent entries fail instead of retargeting another TEB.
On this Rosetta version, automatic LDT allocation and multi-selector installation
abort the process; the implementation explicitly queries these slots and installs
one descriptor per call. Initial isolated experiments observed those limitations.

Original MIT assembly switches into 32-bit code using a far return. Low far-jump
gates switch to 64-bit code at imports, return to the saved host stack, call Rust,
then resume a per-import 32-bit RET-immediate stub with the correct stdcall cleanup.
A final gate returns the DWORD entry result to the host. Host nonvolatile registers
and DS/ES/SS/FS selectors are saved/restored; EBX/ESI/EDI/EBP survive API calls.
Host FS must be unused (selector zero). Host FS is restored before Rust calls,
and guest FS is reinstalled before returning to i386 code. GS is untouched.
Actual DS/ES/SS/FS/GS selectors are compared before/after entry; the leased FS
descriptor is cleared before successful return. No Wine code is copied.

## Loader and API subset

`Image::parse_i386` explicitly selects PE32/i386 headers, 32-bit ImageBase,
directory offsets and four-byte import slots. Existing AMD64 constructors still
reject PE32. Bitness, section bounds/W^X, initialized entry, directory backing,
names/ordinals, arithmetic/32-bit address limits and overlapping fixups are checked.
HIGHLOW relocation may adjust initialized instruction operands or section data
before RX/RO protections; header/BSS writes and unsupported kinds fail. IAT/HIGHLOW
write overlap is rejected. Bounded single-thread static TLS data is enabled for
SizeOfZeroFill=0 with no callbacks. Current startup gates reject TLS callbacks,
nonzero SizeOfZeroFill, SafeSEH dispatch, other active load-config/CFG fields,
bound/delay imports, exception directories, CLR and other existing
unsupported features. For PE32 with 4-KiB section alignment, a partial final image
page now rounds the allocation extent up while retaining the original header
value in `Image::declared_size()`. Section extents must still fit the rounded
mapping, and the one-GiB/32-bit address bounds remain. AMD64 and other section
alignments retain their existing alignment gates. No input header is rewritten.

PE32 certificate directory fields are retained as untrusted file-offset/size
metadata through `certificate_directory()`, without reading or mapping through
them. Ordinary loading does not verify signatures. Explicit FORCE_INTEGRITY
requests fail as unsupported; partial directory pairs remain rejected. The AMD64
certificate file-backing gate and all mapped-directory/section bounds remain.
Callers must separately bound any attempted certificate inspection.

`LoadedImage32::load(bytes, rebase, &process)` preflights every feature/import,
creates the checked image, low gates and guarded stack, and borrows ProcessContext
through cleanup. Unsafe `enter` executes trusted code; it rejects nested entry.
The kernel32 bridge supports GetLastError, SetLastError, GetStdHandle, synchronous
ReadFile/WriteFile, CreateFileW, CloseHandle, UTF-8/UTF-16 conversion,
GetCommandLineW, LocalFree, ExitProcess, GetModuleHandleA/W(NULL) and
GetProcAddress for the current executable. Shell32 supplies CommandLineToArgvW
for the canonical command spelling generated by ProcessContext.
Named module lookup, other module handles and absent export tables remain explicit
unsupported forms. Export-query names must be bounded ASCII in readable guest
section/stack storage; empty/non-ASCII/unreadable names fail before dereferencing
outside checked storage. Success preserves last-error state; tested missing names
return NULL/error 127, and tested out-of-range ordinals return NULL/error 182. Standard handles use actual host stream handles behind explicit four-byte
proxies. Arguments are copied before host calls, allowing output pointers to
alias guest argument words without retaining a Rust reference to that storage.
I/O buffers/count output must lie in permitted guest storage,
with DWORD-aligned stack/count pointers. OVERLAPPED must be NULL, count output
must not overlap the data buffer, and each request is bounded to 16 MiB. Unknown imports fail
before entry; unsupported runtime forms terminate with diagnostic/status 78.

A minimal one-page TEB supplies FS-relative self, stack bounds and last error.
Imported APIs and direct FS last-error writes share the same field. Other TEB
fields are outside this runtime contract. Static TLS explicitly installs its
vector; a zero PEB field and empty SEH-chain marker do not implement those facilities.
The isolated API has no PEB, arbitrary CRT startup, EXE dependency loading or TLS callbacks,
general SEH, guest threads, Windows syscall or binary graphics/COM support on this path.
Only integer/stdcall results are implemented; full floating-point/exception state
and additional calling conventions remain separate. Input instructions are trusted
native code, not statically validated or sandboxed. Existing PE64 runtime/source
compatibility and direct Metal APIs remain separate, preserved paths.

## Isolated PE32 DLL execution

`Image::parse_i386_dll` keeps DLL/EXE and i386/AMD64 entry contracts separate.
`LoadedLibrary32::load` preflights imports, immutable exports and startup features,
then performs real dynamic DllMain(module, PROCESS_ATTACH, NULL). Successful
libraries detach on drop; FALSE initialization receives a single matching detach
before the rejected object is discarded. The process borrow lasts through teardown.
Zero-entry DLLs have no initializer. DLL dependencies, DLL TLS/callbacks, SafeSEH,
CRT startup, a process module cache and reentrant loader operations remain gated.
The existing EXE path does not yet initialize imported DLLs.

`call_name` invokes initialized direct code exports with up to sixteen DWORD
arguments using an explicit `CallingConvention32`. The original CPU return gate
now captures actual guest ESP before recovering the host stack. Both cdecl and
stdcall stack cleanup are checked, including EXE returns; recovering the host stack
cannot hide a convention mismatch. Missing/data/forwarded targets and excessive
arity fail. Each call restores host selectors and releases its bounded FS lease.
GetModuleHandle(NULL) from this isolated DLL is explicitly unsupported because it
has no process executable module; it does not return the DLL as that executable.

Physical M4 development executes owned accepted/rejected DLLs unchanged: real
attach/detach output, repeated five-argument stdcall and three-argument cdecl calls,
HIGHLOW module identity, TEB/stack observations and last-error state. Normal and
forced relocation agree on all 80 DWORDs. A deliberately wrong convention returns
an explicit host error after the real cdecl body and still runs one detach. This
is a host ABI-negative, not a native crash accepted as success. The Windows i386
driver/identical-DLL comparison at clean revision `346f3e0` agrees on all 80 DWORDs
with both hosted Mac and physical M4. Its unchanged actual native report is frozen
at `pe/reference/pe32-library-windows-v1.json` and required by default. See validation
for exact runs and the separate scope of these finite observations.
Game exception/dependency startup remains unsupported, and no game code executes.

## Explicit shared-thread DLL dependencies

`LoadedLibrary32::load_linked` takes already initialized dependencies by basename,
preflights their named/ordinal code/data symbols and binds four-byte IAT slots
before running the consumer's dynamic initializer. Dependencies are borrowed
through detach: the compiler rejects unmapping a provider while its consumer is
live. Related DLLs share one guarded stack/TEB; independently loaded thread contexts
cannot be combined. Duplicate/reserved/path names and missing imports/exports fail
before consumer execution. Imported host APIs can access actual permitted regions
of the entire borrowed dependency closure. No mapping is granted extra rights.

An unchanged frozen owned DLL and a new consumer exercise real code/data imports
in attach, repeated exports and detach on the physical M4. The native Windows
driver dynamically loads the consumer and lets Windows initialize/unload its
dependency. At clean revision `cf234fc`, all 81 raw DWORDs agree across native
Windows, hosted Mac and physical M4, including actual forced relocation. The full
native report is frozen unchanged at `pe/reference/pe32-linked-windows-v1.json`
and required by default. The older isolated-DLL frozen inputs
and API remain intact. This does not implement a filesystem DLL search, automatic
process module cache, DLL TLS/SEH, or EXE static dependency startup. The user's
game remains blocked before entry; no original game files are changed or published.

## Opt-in bounded hardware SEH

`ExceptionImage32` and the launcher's explicit `--seh` option now dispatch real
owned-image UD2 faults through checked FS-linked cdecl handlers. This separate
profile permits validated SafeSEH metadata and enforces membership before calling
a handler. NO_SEH images remain rejected. Ordinary `LoadedImage32` behavior and
its frozen raw-signal observations are preserved; there is no automatic fallback.

A physical M4 experiment first confirmed that Darwin delivers the compatibility
fault in a 64-bit register context, with native FS zero and saved guest FS intact.
The production Rust bridge uses a guarded native alternate stack above 4 GiB,
validates the active thread/image, builds selected Win32 integer/control/segment
context and exception records in checked guest-stack space, and reenters 32-bit
frame handlers. ContinueSearch walks bounded, increasing stack frames;
ContinueExecution validates and applies integer registers, PC/SP and permitted
arithmetic flags before actual kernel signal return. Host signal action, alternate
stack and selectors are restored and queried on return. Metadata inspection alone
does not establish support for the game's handlers.
Entry requires an unblocked default host SIGILL action and exclusive host signal
configuration. Handler changes to the TEB chain head are rejected, alongside
unsupported basic frame/exception-record changes.

The profile supports **UD2 only**, owned-image cdecl handlers and selected integer
context. It rejects imported calls from handlers, unsupported context/registration
changes, unregistered SafeSEH code, nesting and unwind dispositions explicitly.
Other faults, software RaiseException, FP/debug context, system/DLL handlers,
NTDLL dispatcher frames, SEHOP and CRT/C++ exception/unwind support remain separate.
Unused context areas are marked invalid by ContextFlags; their zero storage is not
a fabricated FP/debug observation. Unrelated host signals retain default failure
behavior. This is trusted native execution, not a sandbox or full Windows SEH.

An original owned PE32 uses actual compiler C handlers, assembly registration
frames, a real SafeSEH table and UD2. Physical M4 normal/forced-rebase runs agree
on 32 DWORDs covering search/continuation, seven captured register canaries,
changed EAX/EBX, redirected PC, carry flag and direct FS last-error state. Four
separate host-only negative executables reject explicitly, including a real nested
UD2 and an executable but unregistered handler. Their Windows outcomes are not
claimed. At clean revision `aacce9b`, all 32 raw DWORDs agree with actual Windows
and hosted Mac execution of the identical positive PE. All three PE and 24
conformance CI jobs pass, including actual SDK/MSVC layout/disposition assertions.
The unchanged native report is frozen at `pe/reference/pe32-seh-windows-v1.json`
and required by default. This compares the selected observations, not complete
context bytes, every exception mechanism or the game's handlers.

With explicit `--seh --inspect`, the local game clears bounded exception metadata
inspection and stops at unsupported imports before mapping or entry. No game
instruction runs, and neither its binary nor derived import details enter Git/CI.
Its ordinary loader path still rejects unsupported SafeSEH dispatch.
